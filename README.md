# Medivise

A Flutter application that helps paramedics record patient cases in the field and get
AI-assisted ECG interpretation at the point of care.

Built as a university team project in the Fall 2025 semester. **This project is no longer
under active development** — it is published here as a completed, archived piece of work.

> **Not a medical device.** Medivise was a coursework prototype. Its output is generated by a
> general-purpose language model, has not been clinically validated, and must never be used
> to inform real patient care.

---

## What it does

- **Log a case** — capture patient details (name, DOB) and cardiac risk factors
  (smoker, chest pain, family history).
- **Ingest an ECG** — upload a PDF, CSV, or raw waveform file, or photograph a printed
  strip. Text is pulled from PDFs with Syncfusion and from images via on-device ML Kit OCR.
- **Get an interpretation** — the extracted ECG text and risk factors go to GPT-4o, which
  returns a plain-language reading plus immediate paramedic recommendations, and extracts
  structured vitals (heart rate, PR interval, QRS duration, QTc).
- **Ask follow-ups** — each case gets a chat thread for questions about the diagnosis.
- **Review history** — browse and sort past cases, reopen full details, edit or delete them.

## Architecture

Three pieces, talking over HTTP and Firestore:

```
┌──────────────────┐   REST + Bearer token   ┌────────────────────┐   HTTPS   ┌──────────┐
│   Flutter app    │ ──────────────────────► │  Express backend   │ ────────► │  OpenAI  │
│  (lib/)          │                         │  (backend/)        │           │  GPT-4o  │
└──────────────────┘                         └─────────┬──────────┘           └──────────┘
                                                       │ firebase-admin
                                                       ▼
                                             ┌────────────────────┐
                                             │     Firestore      │
                                             │  cases / chats     │
                                             └────────────────────┘
```

ECG text extraction (OCR and PDF parsing) runs **on the device** in
[`lib/utils/ecg_analyzer.dart`](Medivise/lib/utils/ecg_analyzer.dart), so only the extracted
text — never the raw image — leaves the phone.

`Medivise/functions/` holds a Firebase Cloud Function (`analyzeECG`) that implements the same
analysis flow as a callable function with server-side auth checks and input validation. It was
an alternative to the Express backend and is **not wired up to the Flutter client** — the app
talks to the Express server. It is kept here as part of the project's history.

## Tech stack

| Layer | Stack |
| --- | --- |
| Client | Flutter 3 / Dart 3.8, Provider, `flutter_secure_storage`, `flutter_markdown` |
| ECG parsing | `syncfusion_flutter_pdf`, `google_mlkit_text_recognition`, `image` |

## API

All routes are prefixed `/api`. Everything except `/auth/*` and `/health` requires an
`Authorization: Bearer <token>` header.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/health` | Liveness check |
| `POST` | `/auth/login` | Exchange credentials for a token |
| `GET` | `/user/profile` | Current user's profile |
| `PUT` | `/user/email` | Change email address |
| `PUT` | `/user/password` | Change password |
| `GET` | `/cases/recent` | Five most recent cases |
| `GET` | `/cases/history` | Full case history (`?sort=asc\|desc`) |
| `POST` | `/cases` | Create a case |
| `GET` | `/cases/:caseId` | Fetch one case |
| `PUT` | `/cases/:caseId` | Update a case |
| `DELETE` | `/cases/:caseId` | Delete a case |
| `POST` | `/cases/:caseId/analyze` | Run GPT-4o ECG analysis |
| `GET` | `/chats/:chatId/messages` | Fetch chat thread |
| `POST` | `/chats/:chatId/messages` | Post a message |
| `POST` | `/chats/:chatId/ai-response` | Generate an AI reply |

## Running it locally

You will need your own OpenAI API key and Firebase project. The original project's
credentials are not included in this repository.

**Prerequisites:** Flutter 3.8+, Node.js 18+, a Firebase project with Firestore enabled.

### 1. Backend

```bash
cd backend
npm install
cp .env.example .env          # then add your OpenAI key
```

Download a service account key from your Firebase project
(*Project settings → Service accounts → Generate new private key*) and save it as
`backend/service-account-key.json`. Then:

```bash
npm run dev                   # http://localhost:3000
```

### 2. Flutter app

```bash
cd Medivise
cp .env.example .env          # required: pubspec.yaml bundles .env as an asset
flutter pub get
flutter run
```

Point the app at your own Firebase project by re-running `flutterfire configure`, which
regenerates `lib/firebase_options.dart` and `android/app/google-services.json`.

The client has `http://localhost:3000` hardcoded across the screens in `lib/screens/`. On a
physical device or an Android emulator you will need to change that to your machine's LAN
address (or `10.0.2.2` for the Android emulator).

### 3. Logging in

There are no demo credentials, and none are needed. The login endpoint is a development
stub that accepts **any** email and password (see *Known limitations* below), so enter
anything well-formed — e.g. `demo@example.com` / `demo` — to reach the main app.

## Known limitations

Honest notes on where the prototype stopped, since it was a one-semester project:

- **Authentication is a development stub.** `POST /api/auth/login` accepts any email and
  password and returns a base64-encoded `dev-token-` that the middleware trusts without
  verification. Firebase Auth is initialised in the app but the login flow never uses it.
  The backend must not be deployed as-is.
- **The backend URL is hardcoded** to `localhost:3000` in every screen rather than being
  read from configuration.
- **CORS is fully open** (`origin: true`) — a deliberate testing shortcut.
- **No test suite.** Only the default Flutter widget test scaffold exists.
- **OCR is mobile-only.** Image extraction is disabled on web and desktop; those platforms
  fall back to PDF and CSV input.
- **Two parallel analysis implementations** (Express backend and Cloud Function) with the
  Cloud Function left unconnected.
